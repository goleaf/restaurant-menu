# Migration audit

The 2026-09-14 audit covers all 88 migrations targeting SQLite. Every file defines `up()` and `down()`. An isolated SQLite `:memory:` run completed `migrate → migrate:reset → migrate`, exercising the complete down/up chain without accessing the application database. Forward migrations secure staff and guest invitation credentials, enforce tenant consistency, complete localization and menu media, preserve item-cancellation history, migrate monetary storage to integer cents and add menu-item variants without rewriting historical deployed migrations. The schema retains foreign keys/indexes, soft-deleted history and immutable order snapshots; no view, trigger or stored routine dependency was introduced.

Historical migrations include model-based backfills and therefore present drift risk, but deployed migration files were not rewritten. The current chain contains 88 forward migrations. The additive allergen-snapshot migration was exercised against existing order/ticket rows in an isolated SQLite file: rollback preserved both rows, reapply restored both JSON columns and legacy rows received safe empty-list defaults. Earlier isolated `migrate:fresh --seed`, repeat-seed and guest-invite contraction rollback/reapply evidence remains valid; the contraction preflight still refuses to remove a populated plaintext credential. The application database was never refreshed or truncated. The canonical schema contract is [`data-model.md`](data-model.md).

Empty-database reversibility is not unconditional production rollback safety. Staff/guest credential migrations reject rollback when non-null digests exist. Restoring the old unique `draft_orders.table_session_id` constraint fails after multiple drafts belong to one session. The legacy service-point status rollback maps several states to `unavailable` and cannot reconstruct each original value. Back up and inspect actual data before any rollback; use a forward correction when these preconditions do not hold.
