## Invite-only authorization hardening — complete

- Public Fortify registration is absent from the feature configuration, registered routes, navigation and backend. The only account-creation endpoint is the guest-only, CSRF-protected and `staff-invitations`-throttled invitation registration boundary; route-cache inspection reports four invite routes and zero public `register` routes. The named limiter combines a 10/minute credential/client budget with an independent 30/minute client budget, preventing bypass by rotating guessed tokens.
- `/invite/{token}` now uses a 64-character cryptographically secure bearer whose SHA-256 digest is the only stored representation. The first request immediately redirects to token-free `/invite/pending`; malformed, revoked, expired, mismatched and replayed credentials render localized non-disclosing states. The model remains one-use (`MAX_USES = 1`), and acceptance uses an atomic pending-to-accepted compare-and-set inside the membership/audit transaction.
- New and existing matching recipients converge on the same acceptance Action. Invitations fail closed for unbound recipients, superadmin roles and inconsistent organization/brand/branch chains. Creation, reissue, cancellation and acceptance record token-free audit events with creator/acceptor/expiry evidence.
- Organization and branch staff pages now use `InvitationForm`, display bounded invitation history, search only inside the exact tenant chain, expose creator/created/expiry/acceptor/accepted metadata, and support revoke plus secure reissue. Reissue rotates both digests, invalidates the old link and exposes the replacement only in current authorized Livewire state. No email is sent without a configured delivery integration; administrators copy the current link through a trusted channel.
- `RolePolicy` enforces seeded downward administration: superadmin may manage any non-superadmin role; tenant actors need the relevant capability and may affect only strictly lower roles. Restaurant administrator, director, canonical chef (`head_chef`) and waiter flows are covered. Direct staff Actions, permissions, status changes and waiter-zone assignments repeat policy/tenant checks rather than trusting hidden controls, locked properties or caller-supplied identifiers.
