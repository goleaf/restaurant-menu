# Caching

## Product branch invalidation — 2026-09-14

Guest payload v6 carries responsive primary metadata; v5/v4 and the unversioned legacy key are still invalidated for every supported locale. `ForgetBranchCacheAction` deletes these keys, polling metadata and Laravel flexible creation metadata in one exact-key Eloquent database DELETE when using the concrete standard Repository/DatabaseStore with no relevant listeners. The configured connection/table and literal prefix are preserved, including wildcard-like characters. The database key primary index supports this existing query; no new index is added.

Non-database stores, custom repositories/stores/dispatchers and specific or wildcard cache-event listeners retain normal per-key `forget()` behavior. With the shared database connection, invalidation rolls back with the source mutation. Regression tests cover all versions, refresh timestamps, neighboring branches/apps, file/array support, listeners/custom stores and rollback. This preserves compatibility while reducing the measured common invalidation from 11 queries to 1; it is not a latency claim.

The default cache driver is the database. Cache entries must be explicit and narrow; cache is never used to conceal an inefficient query.

## Dashboard and analytics refresh — 2026-09-15

`BuildRestaurantDashboardAction` caches only its raw report snapshot; current operation cards, readiness and presentation are prepared separately. `BuildBasicAnalyticsDashboardAction` retains its own combined analytics snapshot. Both use versioned database keys (dashboard v5, analytics v5) scoped by currently authorized branches/capabilities, locale, branch generations and a `BranchReportPeriod` fingerprint containing per-branch dates, timezone and currency. Local midnight therefore changes report identity even if the UTC date has not changed. `ViewOrders` remains separate from `ConfirmOrders` in the dashboard access signature. Every request resolves current access before looking up normal or fallback data; the report query receives only branches with `ViewReports` permission.

`Cache::flexible` uses fresh/maximum ages `[45, 60]` for the restaurant raw report and `[240, 300]` for BasicAnalytics. Both numbers are total ages from creation. Fresh hits reuse the report; stale hits return it and schedule regeneration after a successful response; missing or expired entries rebuild synchronously. An ordinary SWR hit does not freeze the restaurant's operational counters or change them to the report's historical dates. Guest menu caching retains its separate availability-sensitive behavior.

The restaurant keeps a separate `:last-success` report for 600 seconds after a successful report lookup. This key retains the permission/branch/period/locale identity but intentionally omits the generation suffix, allowing an explicitly stale older result after a failed synchronous refresh or invalidated-cache rebuild. Its original `generated_at` is retained and presented in the selected branch timezone (UTC for all branches). Failure sets the report's stale state; no prior report produces an unavailable state, not fabricated zero values. This exception fallback can outlive the normal 60-second report age and must not be described as fresh. A changed permission set or period cannot reuse a differently scoped fallback.

Operational cards are recalculated on each dashboard build. A separate actor-and-access-scoped 120-second snapshot supports explicit stale fallback if that calculation fails. It is independent of the financial report period and its 45/60-second cache.

Deferred refreshes retain the originating locale through Laravel's `Localizable` trait and restore the ambient locale afterward. Laravel's per-key database lock is nonblocking and expires after 30 seconds. A busy lock leaves the existing snapshot and expiration intact; an unsuccessful HTTP response does not run the pending refresh. Cold misses still rebuild inline and are not serialized by this refresh lock. Deferred callback exceptions follow Laravel's report-and-rescue behavior; no stale lifetime is extended on failure.

Branch/model observers remove the flexible creation timestamp before removing each indexed snapshot. Laravel checks that timestamp before executing a pending refresh, so invalidation before response termination cancels obsolete work. Each 600-second branch index retains at most 50 keys. When a new access/locale variant displaces an older key, its flexible timestamp and payload are deleted before the index entry is discarded. A queued but not yet started refresh for that displaced snapshot therefore cannot restore it. `BasicAnalyticsTest` exercises both Actions with fresh, stale, expired, locale-switch, invalidation and lock-contention scenarios against isolated database cache tables.

`BranchReportCacheVersion` reads all authorized branch generations in one database cache query. Missing generations use random UUIDs and atomic `Cache::add` initialization with a one-day TTL; concurrent initializers adopt the stored winner. Missing/corrupt metadata never falls back to a shared constant. Invalidation deletes the generation before indexed physical cleanup. A subsequent read therefore cannot discover a late old write or a variant lost by concurrent registry updates. An overlapping read may still finish with its pre-mutation snapshot. No blocking branch lock or request-local authorization/version memo is introduced.

With the default shared database connection, generation deletion participates in the source transaction and rollback restores the old generation. If the cache uses a separate connection, callbacks delete any interim generation again after commit or rollback. The registry remains opportunistic physical cleanup, not the freshness guarantee. Tests cover cold/deferred publication, lost registration, expired refresh leases, scope/locale/permission separation, rollback and separate connections; a real two-process SQLite barrier proves atomic first-generation convergence.

Database cache TTL limits readability, not physical retention of keys that are never read again. `PruneExpiredReportCacheEntriesAction` runs inside actual restaurant raw-report and BasicAnalytics cold/deferred build callbacks, rate-limited by an atomic 60-second marker. `DatabaseCacheEntry` selects at most 500 expired report-family rows using the existing expiration index and rechecks expiration during deletion so concurrently renewed rows survive. The configured named cache connection/table and literal prefix are respected; live, unrelated and other-application entries are preserved. Cleanup failures release the marker and propagate. Ordinary operational refreshes and report-cache hits do not invoke the pruner. Old rows may remain until a later report build or explicit cleanup; no scheduler or worker is required, and no immediate hard bound on total table size is claimed.

## General cache rules

For every entry, code/tests document owner, purpose, versioned key, organization/branch/user/role/locale scope, TTL, stale behavior, invalidation trigger, lock strategy and failure behavior. Cross-tenant, permission-context or locale leakage is a security defect.

Current candidate caches include branch public/menu presentation, dashboard analytics and permission-derived navigation. Locale-neutral domain data may share a cache; rendered/localized payloads include the locale. Branch/menu/model observers or the owning mutation invalidate related entries after successful commit. Database locks protect expensive regeneration where concurrent misses are plausible.

`Cache::touch` is not used unless extending an already-valid entry is the intended product behavior and has hit/miss/TTL/invalidation tests. Cache tags are not assumed because the default database driver does not provide tag semantics. The required test matrix covers miss, hit, correct scope, tenant/locale/user separation, TTL, invalidation, lock timeout and defined fallback.
